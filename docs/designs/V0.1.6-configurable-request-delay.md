# V0.1.6 configurable successful-request delay

V0.1.6 adds one Manager setting named `数据请求成功后等待均值（秒）`. The saved field is
`request_avg_delay`; a missing field loads as 6. Values must be numeric, finite, and greater
than zero.

At each real download-process launch, `EngineService.start()` validates and freezes the current
value in `DOUK_REQUEST_AVG_DELAY`. The snapshot, task log, and `EngineRun` record the same value.
Saving this field while a Manager-owned task is active updates only Manager configuration and the
service used for later launches. It does not rebuild or mutate the running child process. A queued
task reads the saved value when it actually starts.

The compatible engine applies this mean only after successful normal data requests. It retains the
existing log-normal algorithm and 0.5-second floor. Request retry waits explicitly retain a mean of
6 seconds; account batch rest, media retry behavior, link shortcuts, Info batching, proxy, Cookie,
deduplication, paths, identity, logs, and error rules are unchanged.

Automated tests cover 6, 5, 4, missing configuration, invalid values, launch-environment binding,
running-task freezing, the long-link shortcut, short-link GET fallback, Info batching and fallback,
and fixed retry delay. This stage does not claim formal account-scale stability acceptance for 5 or
4 seconds; those graded real runs remain Stage 04 work.
