# 账号汇总 mark 清洗兼容问题

## 状态

- 状态：已确认，待后续 Manager 修复版处理。
- 影响范围：下载结束后的 Manager 账号结果归类与可靠性判定。
- 不影响范围：下载引擎实际账号处理、第二阶段批量 Info 请求与映射验收。
- 当前正式基线：`feature/v0.1.5-final` @
  `2f8dbd42135a60a510b11e10cdfef175360770be`。
- 当前 `develop` @ `8da3e090811fad16a309ceae0d7b0c48530f6f92` 与上述 final 文件内容一致。

本文件只登记问题，不应用候选补丁，不提高版本号，也不重写既有 V0.1.5 历史验收结论。

## 现象与原因

Manager 在任务启动时冻结配置数组位置、A 编号和原始 `mark`。解析下载引擎原生日志时，
当前实现要求日志中的 `标识` 与冻结的原始 `mark` 逐字完全相等。下载引擎用于目录/文件名
的清洗会使少量 `mark` 的表示发生变化，因此 Manager 虽然已经看到完整账号处理块，仍拒绝
将结果归到对应 A 编号，最终把整次账号汇总标记为不可靠。

已确认的 35 项差异为：

| 差异类型 | 项数 |
| --- | ---: |
| 末尾英文句点（包含一个或连续多个） | 31 |
| 连续空格被规范化 | 2 |
| `U+FE0F` / `U+FE0E` 显示变体符被去除 | 2 |
| 合计 | 35 |

按完整账号 ID 将原生日志与晚间账号配置对应后，这 35 项字符差异集合与 Manager 未归类集合
完全一致。这里没有使用响应顺序或从 `mark` 猜测账号，文档也不保存任何真实 ID、链接或
可逆映射。升级前后两轮原生日志出现同一组 35 项差异，进一步说明该问题早于第二阶段批量
Info，不是批量 Info 引入的身份错配。

这些账号不是“未开始”或已证明的下载失败。原生日志账号处理序号完整；缺口来自 Manager
审计层为避免串号而丢弃无法逐字核对的归类结果。

## 候选修复与证据级别

现有外部审计环境提供了一份可审查的 Manager 源码候选补丁。候选方案保留原始 `mark` 全等
匹配，并由冻结计划为已经证明的清洗形式生成预期别名；日志必须完整匹配原始值或该预期值。
如果预期别名与其他账号的原始值或别名冲突，仍拒绝归类，不会仅凭 A 数字前缀猜账号。

外部审计记录的结果为：

- 使用升级前完整运行日志离线回放，账号归类从 1,377 恢复为 1,412；
- 原有 1,377 项分类全部保持不变；
- 35 条身份不一致原因降为 0；
- 67 项下载汇总相关测试通过；
- `git diff --check` 通过；
- 补丁只涉及 `src/douk_manager/core/download_summary.py` 和
  `tests/test_download_summary_parser.py`。

上述结果来自外部审计候选包的源码和离线验证，**尚未经本地 Manager 仓库复核**，不能写成
当前正式 Manager 已修复或本项目维护者已经接受。后续修复版仍需创建独立分支，审查补丁，
运行相关测试与日志回放，并按正常流程完成打包和必要的 GUI 验收。本次文档收尾不应用补丁。

## 历史日志与后续处理

未来升级 Manager 不会自动重算已写入旧 `DownloadTask_*.log` 的账号汇总。正式修复只影响
修复后新生成的汇总；若需要修正历史结果，必须另行设计有明确输入、身份核对和审计输出的
回填流程，不能在升级时静默改写旧任务日志。

另有 [A574 的两条作品地址解析失败](a574-work-url-parse-failures.md)，它在第二阶段升级前已经
存在，属于独立作品级异常，不应并入本问题或归因于批量 Info。

## 对第二阶段验收的影响

该问题不推翻 DouK 下载引擎第二阶段验收：第二阶段全量运行的 1,406 个账号处理序号连续，
Info 请求按 20 上限和 50 账号暂停边界正确切分，且引擎成功/失败总数覆盖全部计划账号。
35 项缺口同时出现在升级前后的 Manager 汇总层，原因已经由 mark 表示差异解释。
